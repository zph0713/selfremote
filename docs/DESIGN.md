# selfremote 架构设计

> 状态：M3.2（协议核心 ✅、分发流水线 ✅、Web 控制面 ✅ ≈ v0.2 全部能力；**v0.3 拆离 server / agent / client / web 四角色 ✅**） · 更新：2026-09-13

## 1. 目标

让在外的人直连「任意一个自己部署的站点内网」（家里 NAS、公司服务器、朋友家…）：

- **内网 IP 直连体验**：在外 `ping 10.200.7.50` 与在家无异（虚拟网段按站点分配）；SSH、SMB、DSM、Web 服务、远程桌面全部可用，无需逐个映射端口
- **多站点统一管理**：所有站点（agent）集中到一台中转服务端；Web 页面上看状态、启停、踢线、下载部署包
- **端到端加密**：两段隧道各自加密（客户端↔服务端、服务端↔站点）
- **单用户私有**：全部自托管，不依赖第三方服务

### 非目标（当前阶段）

- 多租户计费 / 团队协作、跨地域组网（网状）
- 流量伪装与抗封锁（协议预留扩展位，M4+）
- IPv4-only 环境的打洞（M4 中转已可用）
- 家里设备反向访问在外客户端（回流方向）
- Windows 客户端作为验收目标（代码可编译）

## 2. 现状与既定前提（2026-09-13 实测）

| 项 | 状态 |
|---|---|
| 家庭宽带 | 电信双栈，IPv6 可用 |
| 外部可达性 | NAS 已绑定域名，**已验证可从外部经 IPv6 直连访问**；中转服务端只需要一个可达 UDP 端口 |

## 3. 拓扑与数据路径（v0.3）

```
 在外 (Mac)                    中转服务端（任意公网主机）                 站点（可位于 NAT 后）
┌───────────────────┐      UDP/IPv6 或 IPv4      ┌──────────────────────┐      UDP      ┌──────────────────┐
│  sr client        │ ─────────────────────────▶ │  sr server           │ ◀──────────── │  sr agent        │
│  utun: 10.77.0.2  │                            │  用户态中转（无 TUN）  │               │  sr0: 10.77.0.x  │
│  route:           │ ◀───────────────────────── │  注册表 + ACL + 管控   │ ────────────▶ │  ip_forward+SNAT │
│   10.200.7.0/24   │                            │  HTTP 管控 API :8770  │               └────────┬─────────┘
└───────────────────┘                            └──────────┬───────────┘                        │ 站点内网
                                                            │ 状态/指令/注册表                    ▼
                                                    web 控制面（页面 + MariaDB）            192.168.1.x
```

以"在外访问站点 `192.168.1.50`（该站点映射为 `10.200.7.0/24`）"为例：

1. 客户端按路由把目标 `10.200.7.50` 的包送入 utun → 加密 → 发往服务端
2. 服务端解密 → 按**虚拟网段路由表**找到该站点的会话 → 检查 ACL（该客户端是否获准访问该站点）→ 重新加密发给站点
3. 站点解密 → **地址翻译**（`10.200.7.50` → `192.168.1.50`）→ 写入 `sr0` → 内核 `ip_forward` → 出 LAN 前 `MASQUERADE`
4. 回包反向：站点翻译回虚拟网段 → 服务端按 `tunnel_ip` 找到客户端 → 回隧道

**为什么 service 端不需要 TUN**：服务端只做"会话之间的转发"，路由决策由用户态路由表
（站点申报的虚拟网段 → 会话）完成，与内核无关。因此它可以在任意 VPS、容器、甚至笔记本上跑，
只需要一个 UDP 端口 + 一个管控 API 端口。

**为什么站点要用虚拟网段**：多个站点的真实内网常常完全相同（都是 `192.168.1.0/24`）。
站点侧做无状态地址翻译（`real ↔ virtual`，前缀长度相同、保留主机位），客户端只看到唯一
的虚拟网段，两个站点即可同时接入。

**控制面（可选，但推荐）**：nginx + web + mariadb + server + agent-home（见 `deploy/stack`）。

## 4. 组件与仓库结构（v0.3）

| 组件 | 运行位置 | 职责 |
|---|---|---|
| `sr server` | 公网/任意主机（容器或裸机） | 中转：用户态转发、站点与客户端注册表、ACL、防伪造、双链路 MFA、HTTP 管控 API |
| `sr agent` | 站点（NAS/服务器/容器；**主动拨号**） | tun + ip_forward + SNAT（本地网络承接）、地址翻译、网段上报、心跳、执行启停/重连指令 |
| `sr client` | 用户设备（Mac） | utun、路由注入、保活重连、动态码交互、状态展示 |
| `selfremote-web` | 容器 | 控制面：注册/登录/TOTP、站点管理（部署包/启停/踢线/轮换）、客户端密钥与站点权限、仪表盘 |
| `sr gateway` | （遗留）NAS 容器 | v0.2 直连模式：一条隧道直连客户端，仍然可用 |
| nginx / mariadb | 容器 | 反代与存储 |

```
cmd/sr/            CLI（server / agent / gateway / client / genkey）
cmd/web/           Web 控制面入口
internal/tunnel/   协议核心：握手、会话、帧、MFA、注册表、TUN、中转、地址翻译
internal/serverapp/ 中转服务端的管控 API（状态 / 踢线 / 刷新）
internal/webapp/   控制面：账号、站点、客户端密钥、部署包、hub API 客户端
internal/keyfile/  加密配置文件（argon2id + ChaCha20-Poly1305）

deploy/nas/        站点容器（Dockerfile / entrypoint：agent 与 gateway 共用）
deploy/stack/      全家桶 compose（nginx + web + mariadb + server + agent-home）
scripts/           e2e（docker 全链路 / 三容器 hub / 控制面）
docs/              本目录
```

## 5. 协议概览（v0.3）

- 握手：**Noise IK**（X25519 + ChaCha20-Poly1305 + BLAKE2s），双向认证、前向保密
- 数据帧：`[ver][type][nonce:8]` + AEAD（显式 nonce + 64 位滑窗）；类型：握手 ×2、DATA、
  KEEPALIVE、CTRL（预留）、AUTH 三件套、INFO、BYE、AGENT_INFO、AGENT_CMD
- 会话：120s 或 2^20 包重密钥；10s 保活；25s 无收包重连
- MFA：**两条链路都强制**——客户端（人工输码）与站点（配置里的密钥自动应答，无人值守）；
  同一时间步内允许复用（重连不卡 30 秒），跨时间步拒绝重放；3 次失败锁定 30s
- 中转：客户端 ↔ 站点两方向逐包校验（源地址防伪造、目标网段、ACL、在线状态），
  站点间/客户端间默认不可互访；服务端自答 ICMP echo 便于诊断
- 注册表：`clients.json` + `agents.json` 热加载（mtime + 原子 rename），新增/吊销即时生效
- 地址翻译：无状态前缀改写（校验和/分片/IPv6 全覆盖），在站点侧完成
- 细节见 [PROTOCOL.md](PROTOCOL.md)

安全模型：拨号方预置对端公钥（防中间人）；服务端以公钥白名单授权（未授权握手静默丢弃）；
重放由 nonce 单调性 + 时间步窗口防护；站点私钥永不离开配置文件（`.srkey` 加密，服务端
注册表只存公钥）；停止/启用/踢线在管控 API 上（Bearer 令牌，只在内网可达）。

## 7. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 站点或客户端所在网络无 IPv6 | 连不上服务端 | 服务端支持 IPv4 监听（`listen` 可配）；M4 打洞 |
| 服务端成为单点 | 中转全断 | 服务端无状态（注册表在文件、状态在内存），可随时重建/迁移；站点自动重连 |
| 服务端承载全部流量（带宽/CPU） | 速度瓶颈 | 个人使用足够；ChaCha20 软件加解密快；将来可上站点直连（M4） |
| 多站点网段冲突 | 路由歧义 | 控制面强制虚拟网段唯一 + 服务端冲突检测告警 |
| 站点私钥随部署包泄露 | 站点被冒充 | `.srkey` 加密（文件密码）；轮换/重下载即换密钥；站点可随时停用/删除 |
| 群晖内核 `/dev/net/tun` 缺失 | 站点起不来 | 部署清单检查；不支持则改用软路由/小主机作站点 |
| macOS utun 需 root | 体验一般 | 客户端以 root 守护运行；M5 可选 NetworkExtension |

## 8. 决策记录

| # | 决策 | 结论 |
|---|---|---|
| 1 | 项目形态 | L3 覆盖网（tun + 路由 + SNAT），不是端口转发 |
| 2 | 自研深度 | 全自研隧道协议（帧、会话、握手编排）；密码学用成熟库 |
| 3 | 语言 / 部署 | Go；服务端与站点 docker-first，客户端原生运行 |
| 4 | 控制面 | Go 服务端渲染 + nginx + MariaDB；登录与连接双 MFA |
| 5 | 密钥分发 | 网页生成即加密下载（`.srkey`）；服务端只存公钥 |
| 6 | MFA 位置 | 隧道内密封控制帧；未通过前数据双向丢弃 |
| 7 | **v0.3 中转拓扑** | **服务端用户态中转（无 TUN / 无特权），站点主动拨号（可位于 NAT 后）** |
| 8 | **v0.3 站点 MFA** | **站点配置文件携带独立 TOTP 密钥，无人值守自动应答；同一时间步允许重连复码** |
| 9 | **v0.3 网段冲突** | **每站点虚拟网段 + 站点侧无状态地址翻译**（不做服务端逐流转发状态） |
| 10 | **v0.3 分发** | **agent 二进制随 web 镜像发布（CI 构建），网页"下载部署包"直接给出完整 zip** |
| 11 | v0.3 兼容 | 保留 `sr gateway` 直连模式与 v0.2 注册表字段（老客户端/老网关可继续用） |
