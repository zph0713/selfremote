# selfremote 架构设计

> 状态：M1.0（协议核心开发中） · 更新：2026-09-11

## 1. 目标

让 Mac 在任意外网环境（5G / 酒店 / 公司）直连家庭内网：

- **内网 IP 直连体验**：在外 `ping 192.168.1.50` 与在家无异；SSH、SMB、DSM、Web 服务、远程桌面全部可用，无需逐个映射端口
- **端到端加密**：隧道流量仅两端可读
- **单用户私有**：部署在自家 NAS 上，不依赖第三方服务

### 非目标（当前阶段）

- 多用户 / 团队、跨地域组网（网状网络）
- 流量伪装与抗封锁（在协议中预留扩展位，后置 M2+）
- IPv4 直连、中继、打洞（M2）
- 家里设备反向访问在外 Mac（回流方向）
- Windows / Linux 客户端（代码跨平台可编译，但暂不作为验收目标）

## 2. 现状与既定前提（2026-09-11 实测）

| 项 | 状态 |
|---|---|
| 家庭宽带 | 电信双栈，IPv6 可用 |

## 3. 拓扑与数据路径

```
 在外 (Mac)                                       家里 (群晖 NAS)
┌───────────────────┐      UDP over IPv6       ┌─────────────────────────────┐
│  sr client        │  ────────────────────▶   │  sr gateway (Docker)        │
│  utun: 10.77.0.2  │                          │  sr0:  10.77.0.1            │
│  route:           │  ◀────────────────────   │  ip_forward=1 + MASQUERADE  │
│   192.168.1.0/24  │                          └──────────────┬──────────────┘
│        → utun     │                                         │ 内网转发（源地址改写为 NAS 内网 IP）
└───────────────────┘                          192.168.1.x ←─┘  路由器 / 其它设备
```

以"在外 SSH 家里 `192.168.1.50`"为例：

1. Mac 应用发包 → 内核按路由表把目标 `192.168.1.50` 的包送入 utun
2. sr client 加密整包 → UDP/IPv6 → NAS 的公网 IPv6 地址
3. sr gateway 解密 → 写入 `sr0` → 内核 `ip_forward` 转发
4. 出 LAN 前做 **MASQUERADE**：源地址改写为 NAS 自己的内网 IP（`192.168.1.5`）
5. `192.168.1.50` 回包给 NAS → 内核按 conntrack 反向 NAT → 送回 `sr0` → 隧道回 Mac

**为什么 MASQUERADE 是必须的**：内网设备的路由表里没有 `10.77.0.0/24`，不回填的包会被它们直接丢弃（默认网关不认识隧道网段）。改写源地址后，对内网设备而言这次访问"就是 NAS 发起的"，因此**任意内网设备、任意端口、任意协议**都能直达 —— 这正是"内网 IP 直连"的实现方式。

寻址规划：隧道网段 `10.77.0.0/24`；网关 `10.77.0.1/24`；客户端 `10.77.0.2/24`（/24 让客户端内核自动产生隧道网段直连路由）。
NAS 自身服务：经 `10.77.0.1` 或 LAN IP 均可访问（推荐前者，少一跳 NAT）。

## 4. 组件与仓库结构

| 组件 | 运行位置 | 职责 |
|---|---|---|
| `sr gateway` | NAS / Docker（host 网络 + NET_ADMIN + /dev/net/tun） | tun 设备、UDP6 监听、转发 + SNAT（entrypoint 自动配置） |
| `sr client` | Mac（root） | utun、路由注入、保活与重连 |
| DDNS 域名 | 现成 | 解析到 NAS 的 IPv6，客户端连接目标 |

```
cmd/sr/           CLI 入口（genkey / gateway / client）
internal/tunnel/  协议核心：握手、会话、帧、UDP 传输、TUN 设备
internal/config/  配置加载（JSON）
deploy/nas/       Dockerfile / compose / 部署说明
docs/             本目录
```

## 5. 协议概览

- 握手：**Noise IK**（X25519 + ChaCha20-Poly1305 + BLAKE2s），双向认证、前向保密
- 数据帧：`[ver][type][nonce:8]` + AEAD（显式 nonce + 64 位滑窗：丢包/乱序只影响单包）；类型：握手 ×2、DATA、KEEPALIVE、CTRL（预留）
- 会话：120s 或 2^20 包重密钥；10s 保活；25s 无收包重连
- 细节见 [PROTOCOL.md](PROTOCOL.md)

安全模型：客户端预置网关公钥（防中间人）；网关以公钥白名单授权客户端（未授权握手静默丢弃）；重放由 nonce 单调性天然防护。

## 7. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| Mac 所在网络无 IPv6（部分酒店 / 公司 Wi-Fi） | MVP 完全不通 | 已知限制；M2 中转解决。协议已为中继预留 CTRL 帧 |
| 电信 IPv6 前缀变动（重启光猫可能换段） | 客户端连不上 | 复用现有 DDNS；客户端每次连接前重新解析域名 + 断线重连 |
| 裸 UDP 被 QoS / 限速（运营商高峰期） | 速度下降 | 自研协议的优势：M2 可加 TCP/QUIC 外形封装层，无需改动协议核心 |
| DSM 防火墙 / 自身 iptables 冲突 | 规则不生效或被覆盖 | 容器 entrypoint 幂等 `-C/-A` 规则；部署文档给出排查清单 |
| NAS 上转发性能（CPU 较弱） | 速度瓶颈 | 隧道带宽需求不高（<100Mbps）；必要时后续用网卡 offload 或 ESXi 虚机替代 |
| macOS utun 需 root 权限 | 安装体验一般 | MVP 以 root 守护进程运行；M3 可选 NetworkExtension 封装 |
| 群晖内核选项 / `/dev/net/tun` 缺失 | 容器起不来 | 部署前检查清单已列（见 DEPLOY-NAS.md） |

## 8. 决策记录（2026-09-11）

| # | 决策 | 结论 |
|---|---|---|
| 1 | 项目形态 | L3 覆盖网（utun/tun + 路由 + SNAT），不是端口转发 |
| 2 | 家庭节点 | 群晖 NAS，Docker 容器，7×24 |
| 3 | 自研深度 | 全自研隧道协议（帧、会话、握手编排）；密码学用成熟库 |
| 4 | 语言 | Go（TUN/打洞/并发生态、跨平台交叉编译） |
| 5 | 服务器 | MVP 不加公网服务器，纯 IPv6 直连；中转/打洞推迟到 M2 |
| 6 | 部署形态 | docker-first：网关（及未来中继）全部容器化（host 网络 + NET_ADMIN + /dev/net/tun）；Mac 客户端必须原生运行（utun/路由需宿主权限，无法容器化） |

## 9. 待确认清单（部署前收集）

- [ ] NAS CPU 架构（`uname -m`：x86_64 或 aarch64）
- [ ] 家庭 LAN 网段（例如 `192.168.1.0/24`）
- [ ] DDNS 域名全名（客户端 `server` 字段用）
- [ ] Mac 芯片（Apple Silicon / Intel，决定交叉编译目标）
- [ ] 隧道 UDP 端口（默认 `28333`，可改）
- [ ] DSM 防火墙是否开启（需放行该 UDP 端口）
- [ ] NAS 上 `/dev/net/tun` 是否存在；是否启用 Open vSwitch（影响接口名）
